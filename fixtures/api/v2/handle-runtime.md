# Handle server runtime

BACKEND-HANDLE-02 connects the released handle contracts to the existing RunStore, Executor, ArtifactStore and HTTP application. It adds no dependencies and does not implement the TOOLS handle generator or verifier.

`createHandleApplication({ runtimeDir, referenceFiles: { stepPath, previewPath, datumPath }, apiKey?, fetchImpl?, tool?, timeoutMs? })` returns `{ server, store, planner, reference, runtimeDir }`. `timeoutMs` defaults to 180000 and must be positive and no greater than 180000. An absent API key leaves execution unavailable while reference, history, acceptance and export routes remain available.

The operator supplies actual two-pad reference STEP and STL files and the exact UTF-8 `HANDLE_DATUM_CANONICAL_JSON`, without a trailing newline. The factory does not generate reference geometry. Registration copies actual bytes into private, read-only files under `references/handle_mount_reference_v1/`, hashes them and rejects missing, symlinked, empty, oversized, changed or noncanonical input. Existing sealed files must still match supplied bytes on reopen. The instance lock requires a separate runtime per application. A saved state is restored and validated, never replaced with an initial fixture or reset history. Accepted files are revalidated when opening the handle application.

`GET /api/reference` uses the released three-artifact reference union. STEP, STL and JSON download URLs contain no run or acceptance identity. Downloads re-read and hash sealed bytes and carry revision `handle_mount_reference_v1` and applicability `trusted_mount_reference`. Plate reference bytes and headers retain their existing identities.

The optional server entry point selects handle mode with `WORLDKINETICS_DESIGN=handle` and requires `WORLDKINETICS_HANDLE_REFERENCE_DIR`, containing `reference.step`, `preview.stl` and `datums.json`. Default mode remains plate. Missing reference input fails startup. Credentials come from the server environment through the existing operator workflow.

Initial requirements bind the registered mount reference. Initial dispatch has no input artifacts. A follow-up prompt cannot accept the initial handle or switch stages. An explicit requirements PATCH to `handle_refine_v1` resolves the current accepted initial candidate from immutable acceptance history, verifies its eight checks and stored files, and freezes the exact acceptance, STEP, source and check-bundle descriptor into the new requirements. Public bodies cannot supply that descriptor. Refinement always dispatches the original mount separately from the accepted initial input artifacts. All input artifacts belong to that initial revision. Initial and final acceptance remain separate existing CAS operations, and export requires the exact current acceptance and manifest.

Historical refinement descriptors remain valid after final acceptance because restore checks their original acceptance record, not current selection. New enqueue and dispatch require current compatibility. Plate and handle stages cannot be interchanged. Returning to initial requirements after acceptance is rejected. There is no reset route; operator-staged copies of an actual accepted initial runtime can support later rehearsals.

`completeCandidate(candidate, signal?, { retryRejected?: boolean })` is additive. A valid measured rejection can preserve evidence and reserve the next unique attempt/revision in the same serialized transaction. The run stays queued and active, with at most three candidates total. Repair is enabled for the handle application. Failed or unevaluated infrastructure evidence, malformed results and provider failures do not trigger repair. Existing single-attempt callers retain their behavior. `planning`, `running`, `checking` and `fail` accept an optional expected attempt ID to prevent stale mutation of a later attempt. Restart fails only the active candidate and preserves earlier rejection evidence.

The executor uses one AbortController and deadline across provider calls, checks, imports and repairs. Each attempt has its own `runs/<runId>/attempts/<attemptId>/tool-output` directory. Source requests carry exact run/attempt identities, literal stored instruction, frozen requirements, verified accepted source and nullable actual prior rejection feedback. Feedback includes the previous source, source hash and checks; it is never invented. Canonical request fingerprints retain set semantics for checks while dispatched context preserves the supplied check order. Reference and accepted files are checked before provider dispatch and again before CAD dispatch, using shared dispatch validation. The provider rechecks abort after receipt persistence. Receipts and paid attempt claims remain exclusive and are never overwritten or reused.

Tests use explicitly synthetic provider responses, artifact bytes and measurements; they establish state and protocol behavior only.
